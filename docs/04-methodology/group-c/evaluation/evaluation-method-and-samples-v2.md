# SkillVM 评估方法与评估样本 v2.0

日期：2026-10-31。本文规定评估口径；[评估结果](evaluation-results-v2.md)保存逐样本分析与证据；[评估报告](coverage-evaluation-v2.md)给出路线判断。

## 1. 评估目的与边界

评估 **SkillVM 路线对现有九个 Skill 的功能与执行需求的覆盖能力**：哪些需求已有机制可以承接，哪些依赖宿主或外部服务，哪些需要扩展，哪些证据不足。考察完整处理链，不限于 AOT/JIT。

本轮采用文献、固定源码和样本材料进行静态评估。不实现 VM、鸿蒙适配器或端侧工程，不以端侧运行作为本轮完成条件。运行成功率、迁移成功率和性能收益不在本轮统计范围内。

“覆盖”指需求存在有依据的承接方式，不等于已运行成功。尤其区分：接收文件不等于理解并保留全部语义；生成代码不等于具备执行环境；改善效率不等于扩大功能范围。

## 2. 三个分析层次

| 层次 | 问题 | 证据与表达方式 |
| --- | --- | --- |
| 路线设计 | SkillVM 的方法是否适合处理这类需求？ | 论文笔记与机制分析；表述为设计能力或适用性推断 |
| 开源实现 | 固定版本 SkVM 实际提供了什么？ | 代码路径、函数及官方实现文档；不将设计直接写成已实现 |
| 鸿蒙目标条件 | 用于 OpenClaw → HarmonyOS 时还缺什么？ | 对照样本依赖与仓库鸿蒙调研；写明所需条件，不假定已有实现 |

SkillVM 是路线名称，SkVM 是本次核查的上游实现。鸿蒙是项目应用背景；缺少鸿蒙适配器不代表 SkVM 在其已有受支持环境中也无法承接样本。

## 4. 六个评估维度

| 编号 | 维度 | 分析内容 | 不可混淆的边界 |
| --- | --- | --- | --- |
| D1 | 输入与语义保留 | 说明、脚本、references、模板如何进入处理链；功能与约束是否保留 | 复制资源不证明能执行资源；解析name/description不证明实现所有OpenClaw元数据语义 |
| D2 | 能力分析与适配 | 能力画像、需求提取、差距分析与改写/替代路径 | 小测试画像不证明复杂任务正确；改写不等于语义等价 |
| D3 | 工具与依赖承接 | 网络、文件、凭据、命令、协议、平台服务由谁提供 | 可准备的依赖与平台不存在的能力分开 |
| D4 | 运行与宿主衔接 | 适配器、工具执行、多轮状态、持久会话、并行及恢复条件 | 框架适配器不等于业务工具实现；运行钩子不等于任意宿主已接入 |
| D5 | 反馈与优化 | 执行记录能改进什么；哪些代码可复用；何时不适用 | 质量/成本优化与新增功能分开；回退不等于撤销外部副作用 |
| D6 | 验证与可追溯性 | 来源、版本、产物、轨迹、评分与结果对照 | 通用评测设施不自带九个样本的完整业务判据 |

这些是评估维度，不预设 SkVM 均已具备完整能力。AOT主要涉及D2/D3及并行提示，JIT主要涉及D5，输入、运行和验证同样影响覆盖。

## 5. 分项与整体判定

对具体需求使用以下状态，可按子需求拆分，不对整个维度强行打一个分：

| 状态 | 判定依据 |
| --- | --- |
| 已有机制承接 | 固定实现可定位到相关处理路径；只证明机制存在，不证明样本结果正确 |
| 依赖外部能力 | SkVM能够组织或调用，但实际功能由模型、宿主、工具或服务完成 |
| 需要扩展或改造 | 当前核查范围没有满足该需求的现成衔接，须增加适配或替代实现 |
| 证据不足 | 样本或源码证据不足以判断；不按失败或支持处理 |

整体结论按核心功能及决定性缺口归类：

- **指令与资源承接为主**：已知核心需求集中在说明、资源和模型执行，主要适配机制有对应路径。
- **工具绑定决定覆盖**：核心业务依赖可明确列出的工具/服务，路线成立以这些能力可用为前提。
- **专门宿主能力决定覆盖**：核心需求依赖持久进程、复合协议环境或平台服务，不能由通用改写、依赖脚本和运行接口单独补足。
- **暂无法判断**：核心需求或承接路径证据不足。

这些类别描述主要条件，不表示支持程度的数值等级。先做逐样本分析，再归类；完整功能路径不明确时保留局部结论。不能平均各维度得分掩盖核心缺口，也不能把“只读”“仅HTTP”“仅SVG”等子集计作整个Skill。

## 6. 分析步骤与完成标准

1. 按source_id、版本和哈希固定样本，从清单及普查材料提取功能、资源和依赖。
2. 按D1–D6逐项查找SkVM对应机制与源码，明确执行主体；无证据处保留未知。
3. 分别说明受支持宿主中的承接条件及鸿蒙应用时新增的缺口。
4. 给出整体归类、决定性理由和路线建议，并汇总共性问题。

每项结果应能追溯为“样本需求证据 → 机制证据 → 条件/缺口 → 结论”。每个样本还应列出关键语义核对点，例如不漏功能分支、保留上下文和副作用约束；它们用于审查适配方案，不是本轮运行验收任务。

本轮完成标准是九项分析、六个维度和证据链齐全，限制明确、汇总一致。分类数量只称为“样本适用性分布”；鸿蒙端运行覆盖率不计算。

可选补证包括完整包静态复核，或在上游受支持环境中检查某个编译产物是否保留约束。此类实验只回答对应机制问题，不证明鸿蒙可运行，也不是本轮交付前提。
