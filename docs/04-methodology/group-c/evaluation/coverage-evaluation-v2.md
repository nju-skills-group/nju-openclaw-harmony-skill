# SkillVM 路线覆盖能力评估报告 v2.0

日期：2026-10-31。对象：现有九个Skill样本。性质：**完整路线的静态适用性与能力边界评估**。

## 1. 评估目的与核心结论

本报告回答：SkillVM能够承接样本的哪些需求，完整功能依赖什么外部条件，应用于鸿蒙时还缺什么。评估范围涵盖输入、能力分析、适配、工具依赖、宿主执行、反馈和验证，不仅考察AOT/JIT。

**SkillVM对九项样本均存在可定位的材料处理或适配入口，但完整功能覆盖取决于模型、工具与宿主能力，不能由统一输入格式或自动改写直接推出。**

- S01–S03以指令、资源与模型执行为主，与现有路线较匹配。
- S04–S06的覆盖取决于网络、凭据、文件、渲染等工具；SkVM可承担适配和优化，业务能力仍由工具实现。
- S07–S09依赖终端、复合协议/进程或macOS UI服务。在匹配宿主中有承接方向，迁往鸿蒙的关键缺口超出通用适配机制。

本轮不实现VM，不要求鸿蒙适配器或端侧运行，不计算运行覆盖率。以下结论是路线选型依据，不是迁移成功声明。

## 2. SkillVM路线及执行边界

完整链路是：**接收Skill及资源 → 测量目标能力、分析需求差距 → 适配与环境准备 → 宿主执行 → 记录、评测和反馈优化**。

| 组成 | 在覆盖问题中的作用 | 边界 |
| --- | --- | --- |
| Skill加载与资源组织 | 接收正文、脚本、模板和参考资料 | 复制材料不保证功能语义完整，也不提供脚本运行时 |
| 能力画像与需求分析 | 为模型/框架差距提供适配依据 | 小测试画像不能代表完整业务或目标系统权限 |
| AOT适配 | 改写说明、准备可支持的依赖、识别并行机会 | 无法通过准备脚本创造不存在的平台能力 |
| 宿主适配与运行接口 | 将任务交给具体框架执行，提供反馈钩子 | 框架适配不等于实现所有工具、会话和平台服务 |
| JIT反馈与代码复用 | 改进反复出现的问题，减少稳定代码生成 | 需要轨迹和执行条件；收益不等于功能覆盖扩大 |
| 评测与记录 | 对比版本、保留任务和执行证据 | 通用评分无法替代具体Skill的语义判据 |

固定开源实现注册了OpenClaw等宿主适配器，没有HarmonyOS适配器。代码固化的执行后端依赖sh/python3，运行钩子也不是所有适配器都已接通。因此应分别判断路线设计、现有实现和鸿蒙目标条件。具体源码见[评估结果第2、6节](evaluation-results-v2.md)。

## 3. 样本与方法

沿用[c-2a-samples-v1.json](c-2a-samples-v1.json)，L1/L2/L3各三项，固定来源与版本，目的性选样不外推生态总体比例。方法为“功能范围 → 执行需求 → 机制承接 → 外部条件 → 剩余缺口 → 综合判断”。

从六个维度审查：输入与语义保留、能力分析与适配、工具与依赖、运行与宿主、反馈与优化、结果验证与追溯。分项分别标明已有机制、外部依赖、扩展需求或证据不足，不用平均得分掩盖核心功能缺口。

证据来自仓库样本/普查/交接材料及固定SkVM提交 `632cefe42cdade636720d5ef97494d1e5431682b`。9项版本、正文哈希和层级与普查记录一致，此前6项内置正文在线哈希复核通过；完整包仍待复核。详细口径见[评估方法与样本](evaluation-method-and-samples-v2.md)。

## 4. 覆盖结果与代表案例

| 样本 | 核心需求 | SkillVM的作用 | 决定完整范围的条件 |
| --- | --- | --- | --- |
| S01 追问 | 上下文、追问流程、JSON | 组织说明与资源，分析能力差距，调整指令 | 模型及宿主持有跨轮状态；JSON格式不代表追问质量 |
| S02 写作 | 规则、references、事实保留 | 资源承接与指令适配、反馈改进 | 模型读取资源并保持数值与结论强度 |
| S03 第一性原理 | 五阶段、证据与假设 | 明确流程和约束，提供评测入口 | 推理质量由模型执行决定，不能只查阶段格式 |
| S04 天气 | 网络、响应解析、备用路径 | 适配调用与解析流程，提供优化机会 | 宿主网络工具及真实服务；不能缓存旧结果冒充复用 |
| S05 Trello | REST读写、凭据和副作用 | 适配命令/参数、改善错误处理 | 外部认证、业务接口和重试语义；只读不是全功能 |
| S06 制图 | Node、模板、SVG/PNG、远程分支 | 承接脚本资源，分析依赖与可复用逻辑 | 文件、网络、渲染及服务能力；只生成SVG属于子集 |
| S07 tmux | 持久终端和会话 | 识别依赖、组织控制与等待流程 | 宿主PTY/tmux服务，普通shell不能替代 |
| S08 mcporter | HTTP/stdio、OAuth、发现和生成 | 分析分支、通过已有工具组织调用 | mcporter及协议/进程环境；HTTP成功不能代表stdio |
| S09 peekaboo | 屏幕、窗口、输入和权限 | 识别平台依赖、辅助动作流程适配 | macOS Bridge或目标等价UI服务；远程macOS操作对象不同 |

分布为：指令与资源承接为主3项、工具绑定决定覆盖3项、专门宿主能力决定覆盖3项。它描述主要条件，不是成功率，也不表示各类内部所有需求都已确认。

三个代表性区别：S01的主要难点是模型如何遵循说明；S04的主要前提是已有网络工具如何接入；S07的核心是宿主是否真正提供持久终端。三者都可被分析、改写，却不能因此得到同样的覆盖结论。九项完整分析见[评估结果第3节](evaluation-results-v2.md)。

## 5. 鸿蒙目标下的条件和缺口

鸿蒙应用可分为三类工作，不能全部计作SkVM自动完成：

| 工作 | 涉及样本 | 判断 |
| --- | --- | --- |
| 模型、提示、资源及会话接入 | 全部，S01–S03最直接 | 当前实现没有现成鸿蒙适配；这是目标集成问题，不要求为本次研究实现VM |
| 公共业务工具绑定 | S04–S06，S08的HTTP子集 | 网络、文件、凭据等可先列出明确接口需求，是否可复用由目标实际能力决定 |
| 专门运行环境与平台服务 | S07–S09，S06部分运行依赖 | 需PTY/进程、协议环境或UI服务；说明改写和通用运行接口不能单独解决 |

仓库鸿蒙契约用于识别潜在接入差异，其未完成的运行验证不作为本报告的支持证据，也不作为本次静态评估无法交付的理由。

远程Linux/macOS可能保留已有执行能力，但需考虑网络、授权和状态管理；尤其远程macOS截图/输入不等于鸿蒙界面控制。应作为架构选择单独描述，不能用于消除本机能力缺口。

## 6. 路线选择建议与限制

**优先采用适配思路的场景**是S01–S03：用已有加载、能力分析和说明改写机制减少模型/框架差异，重点审查规则、资源与上下文是否保留。

**先核对工具条件再决定引入的场景**是S04–S06：将公共工具需求与每个Skill的适配逻辑分开，判断SkVM能节省哪部分工作。样本已有脚本时，代码固化未必再有明显收益。

**先决定宿主架构的场景**是S07–S09：若核心服务不存在，继续调整提示无法解决主障碍；应明确采用现成服务、限制功能范围或暂不纳入该目标平台，而不是先着手构建完整VM。

当前可直接开展的补证是完整包静态复核、功能分支核对和源码边界审查。上游受支持环境中的定点实验仅作为可选补充，用于回答特定机制疑问，不是本轮完成条件。

限制包括：九项并非随机抽样，完整包未全部复核，未验证改写后的语义等价，也没有质量或成本实测。由此，报告能支持机制适用性和工程边界判断，不能承诺自动移植比例、运行成功率或加速收益。
