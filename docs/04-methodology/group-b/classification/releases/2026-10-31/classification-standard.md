# Skill 可移植性分类标准 v1.0

**乙组 S3｜阶段最终提交版**  
**提交日期：**2026-10-31  
**证据截至：**已收到 S1、S2、E1、E2、E3；E4 未纳入本版。  
**适用范围：**OpenClaw bundled / ClawHub Skill 向 HarmonyOS 智能体迁移时的**静态可移植性评估**，辅以已收到的 OpenClaw 原平台基线测试。

> **结论边界：**本文“最终提交”表示本轮 S3 阶段材料已归档交付，不代表 Skill 已成功移植到鸿蒙，也不代表 74 个 Skill 已被本轮逐文件深读。15 个等级均为**基于现有证据的条件性候选分类**。

## 1. 任务与判定对象

依据《周2-3分工.pdf》，S3 负责制定统一 L1/L2/L3 分类标准、分析和复核代表性样本、吸收其他成员的静态复核与原平台测试结果。S1 负责 bundled 静态普查，S2 负责 ClawHub 静态普查，E 组负责原 OpenClaw 基线测试。

每一个分类必须固定五个要素：

**Skill 身份（owner/slug）＋版本/commit＋原 Skill 的完整功能范围＋必需依赖＋目标 HarmonyOS Agent 能力假设。**

- `SKILL.md` 的内部 `name` 不一定等于 ClawHub `owner/slug`；例如 `davinci-first-principles` 的内部 `name` 不同，应分别记录。
- **完整功能与功能子集必须区分。** 例如 SVG 输出不等于 `meme-maker` 的 PNG/远程 Imgflip 完整功能，简单页面查询也不等于 Notion 的 Workers 等全部工作流。
- 不得将 15 个目的性重点样本的 L1/L2/L3 占比外推到全部 OpenClaw 或 ClawHub Skill。

## 2. L1 / L2 / L3 / 待确认的可操作定义

| 分级 | 判定条件（以所界定的完整功能为准） | 典型依赖 | 必要说明 |
|---|---|---|---|
| **L1：直接或少量修改可移植** | 主要使用模型指令、流程描述、静态资料及目标 Agent **已经具备**的基础工具；不需要重新实现关键执行能力 | 提示词、结构化输出、可直接读取的模板 | 有文件/参考资料要求的场景，需明示“目标能力已提供”的前提；未做目标端验证时只写 L1 **候选** |
| **L2：需要有限适配** | 原有脚本、工具、API、凭据或文件操作要替换，但存在范围可界定的适配途径，预期可保持核心输入输出及错误语义 | `curl → HTTP`、Python小脚本 → ArkTS/兼容执行环境、JSON/文件处理 | 列明替代接口、认证与权限、正常及异常路径；不以某个简单子集代表完整能力 |
| **L3：显著移植障碍** | 完整功能依赖复杂/专有宿主协议、操作系统 UI、交互式子进程、后台服务、复杂 CLI 工作流或大幅度架构改造 | MCP stdio/daemon、macOS 辅助功能、`skill_workshop`、完整 gh 流程 | **L3 不等于无法移植**；应指出具体缺口与可能的架构/运行时方向 |
| **待确认** | 版本、主要功能、外部依赖或目标系统关键能力缺乏证据，尚不足以可靠区分等级 | 原包未取得、外部 CLI 未审计、目标端接口情况未知 | 写清缺什么证据、限制哪个判断；不得强行填满 L1/L2/L3 |

**判断重点是“移植同等功能需要补齐多少能力”，不是“Skill 有几个文件、是否有脚本、用了什么语言”。**

## 3. 推荐判定流程（可复现）

1. **锁定版本与功能范围：**查 `SKILL.md`、ClawHub slug/版本、固定 commit 或清单；描述完整任务和子功能。
2. **检查声明依赖：**包括 `requires.bins/anyBins/env`、OS 门控、安装提示、外部账户及所需凭据。注意安装提示可能仅是推荐，并非所有路径的必需门控。
3. **核对执行路径：**在正文和附属脚本寻找 `exec`、`web_fetch`、`curl`、`gh`、`ntn`、MCP、browser、文件/网络/进程/定时或回调要求。
4. **区分工具语义与程序外壳：**例如 `curl` 是 HTTP 请求实现工具，Python 是脚本运行方式；若可等价替代，应评估功能语义和成本，而不是强制搬运原命令。
5. **逐分支考虑完整能力：**正常路径、备用路径、错误路径、认证/限流、权限、输出格式、状态持久化及用户可见副作用。
6. **按目标能力假设分级：**目标 Agent 已具备且无需关键开发→L1；边界清楚的接口/脚本重写→L2；需复杂运行时或架构→L3；关键证据不足→待确认。
7. **记录证据层级和运行状态：**源码已核/页面已核/仅沿用历史评审，和原平台调用链、功能状态、鸿蒙实际验证分别记录。
8. **审阅新证据是否改变等级：**新增依赖才可能改变移植级别；缺密钥、模型工具调用失败等需先作为环境或执行问题分析。

## 4. 证据可靠性与常见误判

| 证据 | 能够支持的结论 | 不能据此宣称 |
|---|---|---|
| 既有静态普查 | 已有依赖线索和历史等级 | S3 本轮逐项复核了全部内容 |
| 固定版本 `SKILL.md`/脚本/目录 | 文档声明及可见实现的真实依赖 | 在原平台或鸿蒙端已经运行成功 |
| S1/S2 来源、哈希和版本登记 | 调查范围、版本和文件完整性记录 | 未深读的条目已完成深层源码复核 |
| E 组 OpenClaw 日志/输出 | 指定环境/功能子集的实际执行与错误 | 鸿蒙已接入、完整 Skill 已成功迁移 |
| 鸿蒙目标端运行证据 | 其具体测试路径的可用能力 | 未测试的全部功能和不同设备均支持 |

特别注意：

- **无独立脚本 ≠ 无宿主工具依赖：**`weather` 只有 `SKILL.md`，仍依赖 `web_fetch` 或备用 `curl`。
- **原平台成功 ≠ 鸿蒙成功：**E1/E2/E3 的日志是 OpenClaw 基线，不是 HarmonyOS 验收。
- **失败 ≠ L3：**Tavily 缺少 `TAVILY_API_KEY` 主要是认证配置；E3 的 ontology 初轮失败还与模型工具调用能力有关。
- **副作用与安全是独立维度：**E1 发现额外 `write`；E3 的 ontology 安全扫描 suspicious/fail；S2 发现 `mcp-builder` 许可证据不一致。这些都应保留，不必自动改变技术 L1/L2/L3 等级。
- **ArkTS 不是唯一假定方案：**可比较 ArkTS 重写、等价工具接口或经验证的兼容运行时；需真实确认目标环境支持范围。

## 8. 关键争议与本次提交边界

1. **`notion`：**完整 CLI/文件/Workers 并不等同于简单页面请求；当前保留历史 L2 但有 L2/L3 边界争议。
2. **`meme-maker`：**SVG 可用性不能代表 PNG 的 Playwright/Chromium 路径；暂维持 L2，未把 PNG 全功能写成已实现。
3. **`api-gateway`：**S2 重点证据支持完整 L3，单纯只读 REST 可以另列 L2 功能子集。
4. **`mcp-builder`：**LICENSE.txt 引用及 MIT/MIT-0 不一致是来源/许可问题，不直接改变技术等级。
5. **`ontology`：**工具调用依赖模型表现；原平台执行成功与安全性需分别判断。
6. **E4 与甲组未纳入：**本版没有复杂宿主/进程类 E4 动态证据，也没有鸿蒙目标端能力证明。**这不阻塞本次 S3 阶段最终提交，但限制结论的验证层级。**
