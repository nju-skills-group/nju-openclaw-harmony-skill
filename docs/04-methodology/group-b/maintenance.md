# 乙组目录维护说明

## 维护方式

保留原有普查工具和成果目录。S1、S2、S3的上一轮提交按日期归档，原平台实验按成员与案例保存，移植工程放在仓库 `code/ports/` 下。

README作为总入口持续更新，阶段索引汇总成果位置、新增变化和待补事项。阶段归档不作为另一套持续更新的普查数据，也不表示相关变化已经合入原有数据源。

无需每周复制整套表格，也无需把所有成员的压缩包直接上传。

## 上一轮材料怎样保存

### S1：官方样本复核

放在 `skill-survey/bundled/2026-10-31/`：

- `README.md`：复核报告，说明范围、主要变化、证据与限制。
- `survey.csv`：本轮提交的官方样本复核表。
- `survey.xlsx`：对应的Excel版本。

这两个表格是同一轮成果的不同格式，作为阶段归档保留，不分别持续修改。原始普查文件保留在原位置，不用S1表直接覆盖。

### S2：社区样本复核

放在 `skill-survey/clawhub/2026-10-31/`：

- `README.md`：阶段提交说明及文件导航。
- `survey.csv`、`survey.xlsx`：本轮社区样本复核表。
- `focus-review.md`：5个重点样本的复核过程与依据。
- `changes.csv`：相对原表的修改记录。
- `scope-and-limitations.md`：覆盖范围、校验情况与证据限制。

重复的摘要、重复证据索引和原始压缩包可本地留档。只保留摘要而未提交完整校验材料的项目，应明确说明不能据此独立重算。

### S3：分类标准与汇总

放在 `classification/releases/2026-10-31/`：

- `README.md`：阶段提交说明。
- `classification-standard.md`：本轮分类标准。
- `classification-results.xlsx`：重点样本分类结果。

该目录保存当时提交版本，不表示已经替代原普查方法。15项重点分类属于已有样本的汇总，不计为新增普查对象。

S3当时未纳入E4结果，应在说明与阶段索引中标注。后续补充形成修订记录，不将新实验写成当时已经完成。

### E1至E4：原平台实验

放在 `skill-baselines/` 对应成员目录，保留以下材料：

- 基线记录：直接写清功能、实际输入、预期行为、实际输出及测试范围。
- 必要证据：支持结论的日志、工具轨迹、响应、输出文件或截图。
- 复现说明：环境、依赖、调用方式及必要配置说明。
- 问题记录：失败、权限限制、异常行为和待确认事项。

按此前整理后的文件名上传，保留证据目录结构，并修复文档引用。E2复现工具放在 `tools/skill-baseline/e2/`，实验记录与证据放在 `skill-baselines/e2/`。

不必上传整个工作目录、依赖目录、缓存、重复压缩包或无关日志。没有完整原始轨迹时，应明确证据不足，不能用摘要替代完整执行证据。

新的实验保存到新的案例或运行子目录，不覆盖旧日志。文件改名或脱敏后，原校验清单如已失效，应重新生成或暂不提交。

## 原普查数据后续怎样更新

阶段归档与正式数据更新分开进行。本次可以先上传归档，不要求同时修改普查工具。

后续统一审阅S1、S2的有效变化，再合入原有判读数据。需要记录时，在 `skill-survey/review-updates.md` 中注明：

- 样本来源与版本。
- 复核人及日期。
- 修改前后的内容。
- 支撑证据。
- 等级是否变化及原因。

原有结构化判读输入包括：

- `tools/skill-survey/data/bundled-review.json`
- `tools/skill-survey/data/clawhub-review.json`

修改前先确认生成脚本读取的数据源，再同步生成和校验报告。不要只修改生成后的CSV或Excel，导致重新生成时丢失更新。

S3中确认采用的规则再补入原 `skill-survey/methodology.md`，注明修订日期与依据。暂未统一的分类争议保留说明，不强行给出确定结论。

## 本轮移植与Harness材料

每个实际开展移植的案例，在 `code/ports/<skill-name>/` 中保存：

- `README.md`：来源版本、功能范围、配置、运行方法和当前状态。
- `port-record.md`：原功能与依赖、目标接口、具体改动、对照结果和未完成项。
- 实际工程、测试及必要资源。
- 目标端运行证据，或指向证据的链接。

原平台基线继续放在 `skill-baselines/`，在移植记录中引用，不重复复制已有证据。

Harness说明放在 `harness/`，记录OpenClaw版本、关键文件与函数、调用流程及案例对应关系。多个案例共用的机制可以引用，不必重复撰写。同名案例由不同成员独立实现时，用成员子目录区分，避免覆盖。

未开展移植的备选案例自行保存，不提交准备材料。已开展但失败或受阻的案例，仍提交实际改动、已取得的证据及具体阻塞说明。

## 入口与阶段索引怎样更新

- `README.md`：维护本组任务、主要入口和成果使用边界。
- `plans/`：保存各轮工作方案与交付要求。
- `rounds/`：按阶段汇总新增成果、文件入口、结果限制和待补事项。
- 各成果目录的 `README.md`：说明该目录有哪些文件、怎样阅读、适用范围是什么。

阶段索引链接正文和证据，不重复复制全部内容。已合并成果使用相对文件链接；未合并成果可链接PR并标注“待审阅”。尚未上传的材料写“待入库”，不提供不存在的文件链接。

## 日常更新流程

1. 在功能分支上传或修改材料，提交说明写清本次增加或修改了什么。
2. 同一批材料可以分多次提交，集中在一个PR中审阅，无须每个文件单独PR。
3. PR说明材料范围、主要变化、验证结果及未完成项。
4. 按仓库规范经负责人审阅后合并。
5. 同步更新README和阶段索引；可以随成果一并提交，也可以由组长后续集中更新。

## 实验与移植状态

分别记录源码复核、原平台运行、适配实现、构建、业务运行、智能体调用和真机验证。完整功能与功能子集分开，本机执行与远端执行分开。

仅构建成功不称为目标功能通过，仅原平台成功不称为已移植。静态等级也不因一次原平台成功或环境失败自动改变。

旧文档的事实错误可以修订，但应注明原因；原始输出不得改成预期结果。新复测成功不删除旧失败。多次实验的提示、环境或功能范围不同，应分别记录。

## 提交前检查

- 文档和目录使用仓库规定的小写与连字符命名；`SKILL.md`、`README.md`及已有脚本等保留必要命名，避免改名导致调用失效。
- 不提交密钥、签名私钥、账号私密配置或含隐私的完整运行目录；必要脱敏应注明。
- 不强行提交被忽略的依赖目录、缓存和构建产物。较大录屏按仓库约定保存附件链接。
- 第三方源码需核对是否允许再分发；不便提交时，保留固定版本获取方式与哈希。
- 文件改名后修复引用；脱敏或修改内容后检查校验清单是否仍有效。
- 来源版本、执行者、测试范围和验证状态明确。
- 入口与阶段索引中的链接对应实际文件。

本说明规定材料的保存与更新方式，不表示所有目录已经建立、成员材料已经合并，或原普查数据及工具已经完成更新。
