# 周4-5

# 乙组 Skill 移植与 Harness 研究两周工作方案

## 任务一：移植尝试

每人选择两个不同难度的Skill，原则上为一个L1和一个L2，也可延续之前调查或测试的样本，或选择L3。确定一个作为本轮主要移植案例，另一个作为备选。优先推进主要案例，备选根据实际进度开展。

本轮采用个人独立负责方式。允许不同成员选择同一 Skill，但须独立完成所认领的适配和测试，分别保留证据；公共工程、接口说明和问题解决经验可以共享。

真机数量、所在地和可用时间尚未确定。每个人须推进实际适配，清楚记录已完成的验证层级、尚缺接口和设备条件。功能未通过或环境受阻也应提交真实记录，不能以未跑通为由不交材料。

本轮暂不要求每人移植 L3；汇报中仍利用已有 L3 分析和原平台实验解释复杂能力缺口。自动处理 Skill 移植的智能体留待后续阶段研究，本轮仅积累可复用的适配与验收经验。

### 1、移植准备

- 固定版本的SKILL.md、脚本、资源及来源许可。
- 原平台功能、实际输入和输出记录，已有基线可以引用。
- 案例所需的模型、网络、文件、运行时、权限及外部服务。
- 甲组提供的鸿蒙工程模板、注册入口、参数传入和结果返回方式。
- 构建环境和对应调用路径所需的模拟器或真机。

每人针对本轮实际开展移植的案例提交工程改动和移植记录，说明原来如何实现、修改了什么、实际结果是什么，并注明完整功能或功能子集。遇到阻塞，提交已有代码，说明缺少的条件与已尝试的方法。

是否运行成功取决于实际条件。构建、业务运行、智能体调用和真机验证分别记录；不能用准备材料或原平台测试代替实际移植，也不能把构建通过写成移植成功。

### 2、交付物

每人针对移植的样本分别提交：

- **原平台《基线测试记录表》**：已有合格记录可以引用，注明执行者、日期、版本及本人是否重跑。
- **移植代码或工程**：包含实际修改、必要配置及构建运行说明。
- **《移植对照记录》**：说明原功能与依赖、目标接口、具体改动、保留及未实现的功能。
- **运行结果与证据**：实际输入、预期输出、实际输出及日志或截图；未跑通则记录阻塞位置、已尝试的方法和所缺条件。

## 任务二：了解调用skill的Harness工程的代码

Harness在本任务中指支持智能体运行的宿主执行框架，连接模型、Skill、工具和运行环境。

每人结合自己移植的案例查阅OpenClaw源码，了解：

1. Skill怎样被发现和加载，说明怎样进入模型上下文。
2. 模型的工具调用由哪些代码接收、执行。
3. 工具结果怎样返回模型和用户。
4. 移植时需要替换或补齐哪些宿主能力。

### 交付物

每人结合自己的案例提交一份 **《Harness调用链说明》**，包含：

- **源码定位**：OpenClaw版本、关键文件、函数及作用。
- **调用流程图**：Skill发现与加载 → 模型处理 → 按需调用工具 → 结果返回。
- **案例对应说明**：结合运行记录解释实际路径，指出移植时需要替换或补齐的宿主能力。

## 参考格式

### 统一基线测试记录表

本轮实际开展移植的案例，其原平台基线按以下字段记录。已有合格记录可直接引用，缺失内容需补充。

重点是让读者直接看懂“功能是什么、输入什么、实际输出什么”。不能只写“见日志”或“运行成功”；完整输出较长时，表内保留关键内容并链接完整文件。

| 字段 | 填写要求 |
| --- | --- |
| Skill名称与来源 | 名称、bundled或ClawHub、owner/slug、来源链接、版本或commit |
| 功能说明 | 一句话说明功能，并指出本次具体测试哪项功能 |
| 测试环境 | 操作系统、OpenClaw版本、Node版本、模型提供方和实际模型 |
| 安装与配置 | 安装方法、依赖及必要配置；不提交明文密钥 |
| 调用方法 | 完整提示词、触发方式或命令；注明是否人为指定操作步骤 |
| 测试输入 | 实际文本、参数或输入文件，不能只有概述 |
| 预期行为 | 在测试前定义的输出要求、约束及判定规则 |
| 实际输出 | 真实回答、字段、生成文件或错误内容；正常与异常分开记录 |
| 执行证据 | 相关运行日志、轨迹、截图或文件路径 |
| 测试状态 | 成功、功能失败、环境阻塞或未完成；必要时分别列出验收项 |
| 实际依赖 | 运行中观察到的工具、脚本、网络、文件和权限 |
| 后续问题 | 需要分类或目标接口进一步确认的问题 |
| 测试范围 | 完整功能或具体子集，列明未测试部分 |
| Skill使用确认 | 已确认或未确认；给出读取、加载或脚本执行证据 |

既有基线可引用，但必须注明执行者、日期、版本和自己是否重跑。脚本直接运行成功与OpenClaw完整调用链成功分别记录。不同输入、不同功能或不同模型的结果不能拼成一次完整成功。

### 移植对照记录与个人交付

| 字段 | 填写要求 |
| --- | --- |
| 身份与代码版本 | 原样本版本、适配分支或commit、实现人 |
| 分类与功能范围 | L1/L2/L3候选依据、完整或子集、删减与替代项 |
| 执行位置 | 本机、远端或混合；说明每部分在哪里执行 |
| 能力映射 | 原工具/运行时/权限 → 目标接口；已验证或待确认 |
| 具体修改 | 修改的提示、脚本、配置、参数、路径和错误处理 |
| 目标环境 | 工程、SDK、系统、设备或模拟器、模型与调用入口 |
| 对照用例 | 相同业务输入的源端与目标端输出；不可直接对照时解释原因 |
| 判定与差异 | 已通过和未通过项、额外副作用、功能限制 |
| 验证层级 | 构建、业务、模拟器、目标调用和真机分别登记 |
| 证据与复现 | 操作步骤、日志、输出文件、截图或录屏；代测人另记 |

提示类以字段结构、内容约束和行为判断，不要求措辞完全相同。天气、检索等实时服务会变化，可使用固定响应做逻辑测试，但要与真实服务测试分开，不要求不同日期数值一致。

## 每人最终提交清单

每个本轮实际开展移植的案例分别提交：

1. **原平台《基线测试记录表》**：已有合格记录可以引用，注明执行者、日期、版本及本人是否重跑。
2. **移植代码或工程**：包含实际修改、必要配置及构建运行说明。
3. **《移植对照记录》**：说明原功能与依赖、目标接口、具体改动、保留及未实现的功能。
4. **运行结果与证据**：实际输入、预期输出、实际输出及日志或截图；未跑通则记录阻塞位置、已尝试的方法和所缺条件。

每人另提交：

1. **《Harness调用链说明》**：结合移植案例，记录源码位置、调用流程及需要替换的宿主能力。多个案例共用的机制不必重复写。
2. **一页汇报摘要**：汇总功能、输入输出、移植改动、Harness关键点、实际结果及未完成项。

**备选案例未开展移植时自行保存，留待后续使用，不提交准备材料；如果本轮也开展了移植，则按上述要求提交完整记录。完整记录不等于必须移植成功，失败或阻塞也须如实记录。**
