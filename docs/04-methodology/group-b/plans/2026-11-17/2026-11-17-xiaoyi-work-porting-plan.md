# 乙组小艺 Work 独立 Skill 移植计划

2026-11-17。每位组员从[最终候选总表](../../openclaw-xiaoyi-work-inventory.md)自主认领 **1 个 Skill**，在小艺 Work 云电脑中安装并调用改写后的独立 Skill 包。八类分区可按兴趣选择。针对部分覆盖的条目，只认领小艺尚待验证的具体功能。此前的实名分工草案归档留作参考，本轮以认领表为准。 [上一版草案](../2026-11-16/2026-11-16-xiaoyi-porting-plan.md)

## 认领与开工

1. 打开组群共享的[认领表模板](skill-claim-template.xlsx)，每人填一行。填组员名或 GitHub ID、来源、Skill 标识、源版本或 commit、首轮移植功能、计划使用的小艺工具、验收用例及状态。已有阻塞可一并登记。
2. 优先选能用 `SKILL.md`、对话输入和少量静态资料完成的范围。网页、云端文件或脚本类先在 Work 验证所需工具。市场已有相近条目时，用同样例对照一次，登记剩余功能差距。
3. 组长汇总认领、协调重复功能并在群里确定阶段时间。允许同一个 Skill 分别认领可独立验收的不同子集。有重复时先在表里写清各自范围。填完即可做源端基线和本地包准备。

示例可写「ClawHub · `perpetualhui/adaptive-socratic-questioning` · `1.1.0) · 两轮追问并按约定返回 JSON · 模型与会话上下文 · 同一学习目标下核两轮承接和指定字段」。示例仅供填写参考。

## 实施与验收

| 阶段 | 做什么 | 留什么证据 |
| --- | --- | --- |
| 固定源端 | 记录官方 slug 和 commit，或 ClawHub `owner/slug@版本`，核对许可证与依赖。复用合格基线时注明出处及是否本人重跑 | 源端版本、原始输入、预期和实际输出 |
| 制作独立包 | 写清触发描述、输入输出及失败行为。把原依赖映射到 Work 实际可用工具，制作可由 Work 安装的包 | `SKILL.md`、必要配置或资源、打包与安装步骤 |
| 运行对照 | 在同一 Work 云电脑工作区安装，开新会话点名触发。跑至少一条正常用例和一条缺参、异常或权限边界用例 | 实际输入和输出、包标识及版本、可见加载和工具执行记录 |
| 记录证据边界 | 标注安装、Skill 加载、工具成功及业务结果。无可见工具记录时按可见结果登记。可用唯一输出标记或停用对照帮助核验加载 | 对应截图、脱敏日志或可公开链接，注明缺失证据和阻塞位置 |

状态可用「待认领 / 已认领 / 基线中 / 适配中 / Work 测试中 / 已交付 / 受阻」。已交付的状态以提交材料齐备为准，运行结果在对照记录中单列。现阶段所有目标验收以 Work 云电脑为入口。

## 每人提交

| 材料 | 推荐路径 | 内容 |
| --- | --- | --- |
| 移植工程 | `code/ports/<skill-slug>/` | `README.md`、改写后的 Skill 包源码、必要配置和复现说明 |
| 移植对照与 Work 证据 | `code/ports/<skill-slug>/port-record.md` 和可选 `evidence/` | 原范围、移植子集、工具映射、正常与失败用例、实际结果。大附件用受控链接 |
| OpenClaw 原平台基线 | `docs/04-methodology/group-b/skill-baselines/<已有成员目录>/<案例>/` | 新实验按独立案例归档。已有合格记录用链接引用 |
| Harness 调用链与摘要 | `docs/04-methodology/group-b/harness/<skill-slug>-call-chain.md` 和 `<skill-slug>-summary.md` | 简述源端加载、工具调用、结果回传和 Work 的差异。可引用共用机制 |

如同名案例由不同成员独立实现，按维护说明使用成员子目录。提交 PR 时写清本次范围、已验证项和未完成项。组员实填表由组长在群内统一汇总，GitHub 留存空白模板。 [目录与归档规范](../../maintenance.md) · [移植记录参考模板](../../../../../templates/skill-port-template.md) · [Git 工作流](../../../../05-protocols/git-workflow.md)

## 群通知文案
