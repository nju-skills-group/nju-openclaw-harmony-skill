# 乙组 Skill 分类与移植

乙组研究 OpenClaw Skill 的功能、执行依赖及向鸿蒙迁移的方法。本目录汇总普查与复核、原平台基线、Harness 源码分析和移植进展。实际移植工程统一放在仓库 `code/ports/` 下。

当前工作包括**实际移植与 Harness 了解**。每人选择两个不同难度的候选案例，原则上为 L1、L2 各一个，也可继续使用此前调查或测试过的样本，或选择 L3。确定一个作为本轮主要移植案例，另一个作为备选。

每个实际开展移植的案例均提交代码、移植记录和运行证据；未开展的备选自行保存，不提交准备材料。同时结合案例查阅 OpenClaw 源码，说明 Skill 的发现与加载、工具执行及结果返回过程。实现进度与验证结果分别记录，设备或接口尚不可用时如实说明。

## 已有成果与使用边界

原始普查以2026年10月25日记录的材料范围为依据：50项官方 bundled Skill，以及按8类依赖形态选出的24项 ClawHub 社区样本，共74条来源与版本记录。社区样本是目的性选样；不同来源的同名 Skill 分别保留，不能将74条记录解释为74种独立功能，也不能据此推算整个生态的可移植比例。

上一轮 S1、S2 沿用这74项，分别重点复核5项。新表没有新增样本，也没有改变原有基础 L1/L2/L3 等级，主要补充依赖细节、证据位置和复核状态。

S1、S2提交的表格按日期保留为阶段归档，不作为另一套持续更新的普查数据。后续确认有效的修改，再合入原有判读数据并重新生成报告。

S3在既有标准上细化“待确认”、适配路径和判定流程，并吸收部分运行结果。其上一轮提交版作为阶段归档保留，后续修订应说明变化与依据。

E组提交涉及6个实际测试样本，覆盖提示执行、网络服务、脚本和宿主工具。各案例的功能范围与证据完整度不同，不能合称6个完整 Skill 全部通过。

上述材料尚不构成鸿蒙移植成功证明。具体结论应结合各案例的功能范围、实际输入输出和目标端证据判断。

## 怎样阅读一个案例

按照“原始样本与静态依据 → 原平台输入输出 → Harness及工具依赖 → 适配实现 → 目标端结果”阅读。尚未完成的环节标注当前状态。

- **weather：**S1重点复核 → E2原平台正常、备用及超时记录 → S3候选L2结论。适合观察网络工具如何映射为目标能力。
- **healthcheck：**S1重点复核 → E4三条只读命令及后台任务记录。该实验尚未纳入上一轮S3提交版，后续汇总时应补充。
- **ontology：**脚本级Project—Task关系流程与Agent创建Note流程分别记录，不合并成同一功能的完整成功。

各案例的文件入口和证据限制见[上一轮成果索引](rounds/2026-10-31.md)。

## 本轮交付要求

每个实际开展移植的案例分别提交：

1. **原平台《基线测试记录表》**：已有合格记录可以引用，注明执行者、日期、版本及本人是否重跑。
2. **移植代码或工程**：包含实际修改、必要配置及构建运行说明。
3. **《移植对照记录》**：说明原功能与依赖、目标接口、具体改动、保留及未实现的功能。
4. **运行结果与证据**：记录实际输入、预期输出、实际输出及日志或截图；未跑通则说明阻塞位置、已尝试的方法和所缺条件。

每人另提交一份**《Harness调用链说明》**及**一页汇报摘要**。多个案例共用的Harness机制不必重复写。

未开展移植的备选案例自行保存；如果本轮也开展了移植，则提交上述完整记录。完整记录不等于必须移植成功，失败或阻塞也须如实记录。构建通过、业务运行、智能体调用和真机验证分别登记。

## 更新原则

1. 保留 `skill-survey/` 及既有相对路径，优先增量修改，不为整理外观搬动全部材料。
2. 普查数据按现有生成流程维护：先修改对应判读输入，再生成CSV、JSON、Markdown和Excel，避免分别手动维护多个冲突版本。
3. 阶段归档保留当时结论。后续修订通过新记录和链接说明，不将历史提交改写为已经完成的新工作。
4. 新运行保留独立证据。后续成功不覆盖历史失败；摘要可以更新，但须注明依据。
5. 每次阶段汇总只写新增变化、成果位置和未完成项，不复制整套旧成果。
6. 文档与工程改动使用功能分支，按仓库规范经PR审阅后合并。一次整理可以集中为一个PR，无须每个文件单独提交。
7. 上传前检查密钥、账号及个人信息，保留必要的脱敏说明；文件改名后同步修复引用。

本入口随成果合并情况更新。标注“已完成”的内容应提供对应文件或证据入口。
